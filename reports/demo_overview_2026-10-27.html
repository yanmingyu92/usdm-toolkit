usdm-toolkit — what has been done so far

An independent, open-source toolchain that reads the published USDM v4.0.0 deliverables and checks them against each other, generates SDTM Trial Design domains, and executes JSONata conformance rules.

1Background

While onboarding as a DDF volunteer, I read the USDM v4.0.0 deliverables end to end — and on 21 Oct 2026 three new issues appeared (#716, #717, #718) reporting inconsistencies between dataStructure.yml and USDM_CT.xlsx. Instead of eyeballing them, I built a small tool to check the two files against each other mechanically — then kept going with two more modules aimed at the USDM→SDTM path described in Implementation Handbook 1.

  • #716 — 27 attributes where the YAML carries the C-code of a concrete subclass while the CT row for the abstract class says otherwise.
  • #717 — Procedure.procedureType has no value list (free string, not comparable across studies).
  • #718 — ExtensionAttribute/ExtensionClass still present in dataStructure.yml although they were decided to be API-only (#613).

All three were independently reproduced, 100%, with a separate implementation — and the checker surfaced 7 additional findings the issues don't mention.

2The toolkit — three small modules

ct-align

Cross-checks dataStructure.yml against USDM_CT.xlsx: C-codes, preferred terms, definitions, value-list/type agreement, coverage in both directions. 9 consistency rules, ~2 seconds per run, CI-friendly exit codes.

trial-design

Generates SDTM Trial Design domains (TS/TA/TE/TV/TI as CSV) from a USDM v4.0 study JSON — the USDM→SDTM path of Implementation Handbook 1, with every path→variable mapping and assumption documented.

rules

A small conformance-rule engine: rules are YAML files with JSONata boolean expressions. The bundled starter library is mechanically derived from the required (cardinality 1 / 1..*) attributes in dataStructure.yml — nothing hand-invented.

Disclaimer. usdm-toolkit is an independent, community-driven open-source project — not developed, endorsed, or reviewed by CDISC or the DDF team, and not part of the official DDF-RA deliverables. It only reads the published files (pinned to tag v4.0.0); findings are the author's interpretation and should be verified against official sources. The USDM model and CT remain the property of CDISC under its license terms.

5rules — JSONata conformance engine

The five starter rules are mechanically derived from the required attributes in dataStructure.yml (cardinality 1 or 1..*):

RuleSeverityScopeConstraint
USDM-REQ-001errorStudyVersion≥1 study identifier (1..*)
USDM-REQ-002errorStudyVersion≥1 study title (1..*)
USDM-REQ-003errorStudyArmmust have a type code (1)
USDM-REQ-004errorEncounternon-empty name (1)
USDM-REQ-005errorInterventionalStudyDesignmust have an intervention model code (1)
 
# valid instance — 5/5 rules pass, exit 0
$ python -m usdm_toolkit.cli rules --input data/examples/complex_1.json --out reports/demo_rules.md --format md
rules: 0 violations written to reports/demo_rules.md

# negative control — titles emptied on purpose: the right rule fires, exit 1
$ python -m usdm_toolkit.cli rules --input reports/demo_broken.json --out reports/demo_rules_broken.md --format md
rules: 1 violations written to reports/demo_rules_broken.md
USDM-REQ-002 | error | StudyVersion | StudyVersion_1 | expression evaluated to False

7Reproduce it in 3 commands

# Python 3.10+; source files pinned to DDF-RA tag v4.0.0
git clone https://github.com/yanmingyu92/usdm-toolkit && cd usdm-toolkit
pip install -e .

# 1) model vs CT consistency (~2 s; exit 1 = errors found, by design for CI)
python -m usdm_toolkit.cli ct-align --yaml data/source/dataStructure.yml --ct data/source/USDM_CT.xlsx --out report.md

# 2) USDM study JSON -> SDTM Trial Design CSVs
python -m usdm_toolkit.cli trial-design --input data/examples/complex_1.json --out trial_design_out

# 3) JSONata conformance rules
python -m usdm_toolkit.cli rules --input data/examples/complex_1.json --out rules_out.md

Tests: pytest. Everything is deterministic and derived from the published files — no hand-maintained finding lists.
